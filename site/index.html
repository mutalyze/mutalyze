How ruleguard checks every session

Learn more

Every repo has a CLAUDE.md. Agents follow it at first, then quietly stop — nothing errors, nobody checks. ruleguard reads your rules and one session transcript and reports which rule broke, at which turn, with the literal evidence. Deterministically. No LLM decides.

How it works

Compile your rules. Execute against the log.

Two strictly separated phases. Phase one may think hard, once. Phase two is deterministic — no LLM, no network — so every finding is a fact you can open the transcript and see.

# CLAUDE.md → .ruleguard/
- Use `rg`, not `grep`.
- Read before editing.
id: CM005 type: command
forbid: [grep]
scope: repo

Step 03

Cite

Every violation names a turn, the line's id, and the literal evidence — so you don't trust a verdict, you verify it. The rule's own text is kept attached, ready to re-assert.

Three verdicts

Violated, held — or unresolved.

Most tools give you two answers. The third is the honest one: when the evidence is ambiguous, ruleguard says so instead of guessing.

Violated

The rule broke.

A real, in-scope event that breaks the rule — cited to the turn with the literal command or added line. A violation always rests on evidence you can stand behind.

Held

The check ran and passed.

Not silence — a check that was applicable and stayed satisfied across the session. Held is only ever reported when the check actually ran.

Unresolved

Can't locate it — won't claim it.

A command whose directory came from a shell variable can't be placed in or out of scope. It's reported apart, never counted as a violation and never dropped. You can still open the turn.

What it reads
Three check types

The rules are on disk. The record is on disk.

ruleguard is the part that checks one against the other — reading the tool-call payloads themselves, not just their names.

commandscans Bash inputs — “Use rg not grep.” contentscans Write / Edit added lines — “No console.log.” orderingscans the sequence of tool calls — “Read a file before editing it.”
.ruleguard/checks.yaml
version: 1
- id: CM002
  rule: Never commit directly to `main`.
  type: command
  forbid_pattern: git\s+commit
  when_branch: main
  scope: repo

unsupported:
  - Write clean, maintainable code.
    ↳ not mechanically verifiable
Built-in

A safety pack that needs no rules file.

Checks nobody writes down but every repo wants — shipped with their verifier, authored precisely, session-scoped. So a first run is never fully silent.

SP001
Never force-push.

--force / -f — but not the safe --force-with-lease.

SP002
Never pipe the network into a shell.

curl … | sh — heredocs and quoted docs don't count.

SP003
Never rm -rf a home or root path.

Recursive deletes of ~, $HOME, or system paths — not your temp dir.

SP004
Never write a key to a credential file.

A secret landing in .env or id_rsa — example files and fixtures excluded.

Honest by default

What it won't do.

The instrument is only worth trusting if it's straight about its own edges. These are in the README, not the fine print.

→
Checkable rules skew trivial.

The rules easy to check mechanically usually aren't the ones that matter. The ones that do get marked unsupported — counted, never faked.

→
“Secrets to disk” is destination-scoped.

It catches a key written to .env or id_rsa — not one hard-coded into config.ts. It is not a full secret scanner, and doesn't pretend to be.

→
A quiet run is not a clean bill of health.

Zero findings can mean the agent complied — or that your rules compiled to unsupported. Read the compiled / unsupported counts, not just the violation number.

Local by default

Your code never leaves your machine.

A default run computes everything locally and prints a report. It transmits nothing and phones nothing home.

The optional team payload — ruleguard check --signals — sends only hashes, categories, and counts. Never a command, a path, or a rule. A leak-guard re-checks the payload and refuses if any raw content slipped in. --signals is a flag, never a default.
